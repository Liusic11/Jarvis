# JARVIS 架构设计

本文档记录 JARVIS
的长期定位、架构原则、设计决策与实现约束。实现前先读这份文档。

------------------------------------------------------------------------

## 1. 定位与范围

### 1.1 长期定位

JARVIS 是一个长期演进的个人 AI
Agent：能够理解主人提出的任务，通过不同交互入口与主人沟通，并通过可替换的能力模块与数字世界和物理环境交互。

长期目标更接近《钢铁侠》中的
JARVIS，而不是一个只负责智能家居的语音助手。它不应绑定某个设备、模型、Harness
或应用生态。

**智能家居是第一个应用场景，不是项目边界。**

长期可能扩展到
Web、电脑操作、文件、日程和多步骤任务协调。但这些是方向，不是当前阶段的建设清单。

### 1.2 当前范围

当前优先做任务型闭环：用户提出任务，JARVIS
理解任务、调用能力、核验结果并回复。

当前先用文字入口和 Home Assistant
虚拟设备验证架构。主动式行为、长期记忆、复杂任务编排和真实硬件接入暂缓。

**现在还没有真实家庭硬件。** 设备全部是 Home Assistant
中的虚拟设备，用来验证能力接口和操作闭环。

------------------------------------------------------------------------

## 2. 架构原则

### P1. 解耦（Decoupling）

模块有清晰职责，通过明确接口协作，不依赖其他模块的内部实现。替换一个模块时，尽量只修改该模块及其适配层。

### P2. 可迁移（Portability）

不把 JARVIS
绑定在单一模型供应商、Harness、操作系统、硬件或设备生态上。配置、数据和能力接口应尽量与运行环境分离。

### P3. 可替换（Replaceability）

模型、Harness、插件、语音入口、外部服务都允许升级、替换或移除。技术选型应考虑未来迁移成本，而不只考虑今天接入是否方便。

### P4. 故障隔离与优雅降级（Graceful Degradation）

单个插件或外部服务不可用，不应拖垮整个
JARVIS。能力应尽量独立部署、独立测试、独立恢复；不可用时应明确报告降级状态，而不是假装成功。

### P5. 不重复建设基础设施

优先采用成熟的 Agent
Runtime、模型服务、语音生态和设备网关。只有现有生态无法满足明确需求时，才自研对应组件。

**核心原则：JARVIS 应该拥有体验，而不是拥有基础设施。**

JARVIS
应掌握的是稳定的核心契约、身份与上下文、权限规则，以及不同组件协同工作的整体体验；不需要为了"拥有"而自己实现模型、Harness、语音引擎或设备网关。

### 2.1 技术替换检验

引入一个新组件或技术方案时，至少问：

1.  如果未来换成另一个模型 / Harness / 服务，哪些代码需要修改？
2.  是否能通过适配层或配置完成替换？
3.  组件不可用时，其他能力是否仍能工作？
4.  是否把某个供应商的专有数据结构泄漏到了核心逻辑？
5.  是否有测试或评测能证明替换前后行为没有退化？

如果替换一个组件需要大规模重写其他模块，应重新审视耦合边界。

## 3. 长期参考架构

这是目标架构的逻辑分层，不代表当前需要一次性实现全部模块。

``` text
┌─────────────────────────────────────────────┐
│ 交互层（Interaction Layer）                  │
│ 文字 / 语音 / 手机 / 桌面 / 屏幕              │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ Agent Runtime                               │
│ Harness / 模型 / 工具调度 / Session          │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ JARVIS Core Contracts                       │
│ Identity & Context / Permissions             │
│ Memory / Task State（后续按需引入）           │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ 能力层（Capability Layer）                   │
│ Home / Web / Screen / Computer / Files / ... │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ 外部系统（External Systems）                 │
│ Home Assistant / OS / Internet / Devices     │
│ Applications / Third-party Services          │
└─────────────────────────────────────────────┘
```

### 3.1 各层职责

  -------------------------------------------------------------------------------------------------------------
  层                      职责                                     设计要求
  ----------------------- ---------------------------------------- --------------------------------------------
  交互层                  接收用户输入、呈现结果                   入口可替换，不承载核心业务规则

  Agent Runtime           对话循环、模型调用、工具调度、会话运行   优先使用成熟
                                                                   Harness；避免把业务逻辑写死在某个 Runtime

  JARVIS Core Contracts   定义身份、上下文、权限等稳定概念         由项目掌握接口；保持轻量，不提前做成大框架

  能力层                  提供 Home、Web、Screen 等具体能力        插件独立、结构化输入输出、可单独测试

  外部系统                实际执行动作或提供数据                   通过适配器接入，不让供应商细节渗入核心
  -------------------------------------------------------------------------------------------------------------

### 3.2 Core Contracts 的引入顺序

-   **当前优先**：Identity & Context、Permissions。
-   **后续按需**：Memory、Task State。
-   不因为长期架构图中出现某个模块，就提前实现它。
-   Core Contracts 是稳定的接口和数据约定，不是另一个自研 Agent
    Framework。

## 4. 当前实现结构

当前采用 Harness + 插件的路线：

``` text
用户（当前以文字入口为主）
        │
        ▼
Harness（候选：DSH / pi / 其他）
  对话循环 · 模型调用 · 工具调度 · 会话管理
        │
        ├── JARVIS Identity / Context
        │
        ▼
结构化工具接口
        │
        ├── home 插件 → Home Assistant → 虚拟设备
        ├── web 插件  → 搜索 / 网页读取（待做）
        └── screen 插件 → 电视 / 电脑屏幕（待做）
```

  -------------------------------------------------------------------------------------------------------
  组件                    当前职责                       替换原则
  ----------------------- ------------------------------ ------------------------------------------------
  Harness                 Agent 运行环境                 插件通过薄适配层接入，不依赖 Harness 内部实现

  模型                    理解任务、选择工具、组织回答   允许更换 API 或本地模型；更换后重新跑评测

  插件                    提供具体能力并返回结构化结果   独立包、独立测试、可安装和移除

  Identity / Context      提供 JARVIS 身份和相关环境信息 与插件实现分离；逐步从静态文本演进为动态上下文

  外部系统                实际执行操作                   通过适配器接入，避免核心代码绑定某个供应商
  -------------------------------------------------------------------------------------------------------

### 不可违反的安全约束

**模型只能调用插件暴露的结构化工具，不能直接获得外部系统的密钥或底层访问凭据。**

-   模型认识的是 `home_call_service(domain, service, entity_id)`，不是
    Home Assistant URL。
-   HA token 只存在于插件进程或插件后端，通过环境变量或本地 `.env`
    读取。
-   插件返回结构化结果，自然语言由 Harness / 模型组织。
-   高风险动作必须在代码层实施权限检查和确认，不可只靠 prompt 约束。

### 5.2 插件与 Harness 的适配原则

DSH、pi 等 Harness
的插件接口可能不同。项目定义自己的最小公共契约，Harness
专属代码限制在薄适配层。

目标不是保证插件源码在所有 Harness 中完全零修改，而是保证：

-   插件核心逻辑不依赖 Harness 内部模块。
-   工具定义、参数 Schema、结构化返回值有稳定约定。
-   迁移 Harness 时主要修改适配层和部署配置。
-   每个插件可脱离 Harness 单独测试。

## 7. 虚拟家庭

全部定义在 `homeassistant/config/packages/virtual_home.yaml`，由
`input_boolean` / `input_number` / `input_select`
作为状态载体，派生出带真实 domain 的实体。

  房间   设备
  ------ ----------------------------------------------
  客厅   灯、空调、窗帘、电视、存在传感器、温度传感器
  卧室   灯、空调、窗帘、存在传感器、温度传感器
  书房   灯、空调、存在传感器、温度传感器
  厨房   灯、存在传感器、温度传感器
  玄关   前门锁、存在传感器
  全屋   扫地机器人

完整清单见 [`VIRTUAL_HOME.md`](VIRTUAL_HOME.md)。

关键点：

-   保留真实 domain（`light` / `climate` / `cover` / `media_player` /
    `lock` / `vacuum` / `sensor`），换真实设备时 service
    调用形态尽量不变。
-   空调用 `generic_thermostat`，电视用 `template switch`，其余用
    `template`。
-   不提交 HA 的 `.storage/`、数据库和日志。
-   已知问题：客厅灯关闭时，带亮度调用 `light.turn_on`
    只会改亮度，不会把灯打开；尚未修复。

## 8. 插件约定（初版）

每个插件应：

1.  独立成包，不依赖某个 Harness 的内部模块。
2.  对模型暴露工具名、说明文字和参数 JSON Schema。
3.  返回结构化结果（如 `{ok, ...}` 或
    `{ok: false, error}`），不直接返回自然语言。
4.  不包含 JARVIS 身份、人设或个人习惯。
5.  从环境变量或 `.env` 读取密钥，不硬编码。
6.  可单独测试，不启动 Harness 也能调用核心工具函数。
7.  对外部系统实施必要的超时、错误映射和输入校验。
8.  不可用时返回明确错误，不把失败伪装成成功。

不同 Harness
的协议差异由薄适配层处理。插件公共契约应尽量小，避免为了抽象而抽象。

## 9. Identity、Context 与 Permissions

### 9.1 Identity

Identity 描述 JARVIS
是谁、如何沟通、遵循什么基本行为原则。它不应该散落在各个插件里。

当前先通过 Harness 启动时注入 system prompt。内容可分为：

-   人设：身份、表达方式、基本行为准则。
-   环境：当前家庭结构、可用设备等相关信息。
-   习惯：用户明确提供且适合长期使用的偏好。

### 9.2 Context

Context
是完成当前任务所需的动态信息。家庭设备清单等容易变化的信息，不应长期硬编码在静态
prompt 中。

当前阶段可先使用静态信息完成最小闭环；后续应评估从 HA 或 Context
Provider
动态获取相关信息。只向模型提供当前任务需要的上下文，避免无差别塞入全部元数据。

### 9.3 Permissions

权限必须由代码执行层落实，而不是只写在 prompt 中。

-   普通读操作可按插件策略开放。
-   普通设备控制按明确的允许范围执行。
-   高风险操作（如门锁）需要显式确认。
-   插件不得因模型要求而绕过权限策略。
-   权限检查应独立于 Harness，避免更换 Runtime 后安全规则失效。

### 9.4 暂不建设的部分

Memory 和复杂 Task State
是长期架构中的可能模块，但当前不实现。先验证用户发起任务的闭环，再根据实际需求决定记忆内容、生命周期和存储方式。

## 10. 模型与评测

-   当前 spike 使用 DeepSeek API。
-   后续可以评估其他 API 模型或本地模型。
-   模型更换不应要求重写插件，但会影响工具选择、参数准确性、速度、成本和上下文预算。
-   **模型可替换不等于模型行为等价**：每次更换模型或重大升级后，都应运行同一套
    evals，比较工具选择、参数、权限遵守和任务结果。
-   本地模型硬件规划不构成当前架构依赖；不为某个预设模型尺寸提前设计复杂系统。

## 12. 配置与可移植性

环境变量统一使用 `JARVIS_` 前缀。

  变量                                        说明
  ------------------------------------------- ---------------------------------------
  `JARVIS_ENV`                                `dev` / `prod`
  `JARVIS_HOST` / `JARVIS_PORT`               Python 服务监听地址
  `JARVIS_HA_URL`                             HA 地址，默认 `http://localhost:8123`
  `JARVIS_HA_TOKEN`                           HA 长期访问令牌，不提交
  `JARVIS_HA_TIMEOUT_SECONDS`                 HA 请求超时
  `JARVIS_LLM_PROVIDER`                       `stub` / `ollama`
  `JARVIS_OLLAMA_URL` / `JARVIS_MODEL_NAME`   Ollama 配置
  `JARVIS_DATABASE_PATH`                      SQLite 路径
  `JARVIS_CONFIRM_HIGH_RISK`                  高风险操作确认开关

完整说明见 `.env.example`。

### 禁止硬编码

文件系统绝对路径、用户名、IP 地址、机器专属配置、API key、密码和 HA
token，全部走环境变量或本地配置文件。

### 跨平台注意

  问题               处理
  ------------------ -----------------------------------------
  Shell 脚本换行符   `.gitattributes` 强制 `*.sh` 为 LF
  Windows 路径       使用 `pathlib` 与相对路径
  HA 在 Windows      当前通过容器运行
  Docker GPU 直通    Compose profile 控制，无 GPU 机器不启用

### 数据与状态迁移

-   代码、可复现配置和虚拟家庭定义可通过 Git 同步。
-   密钥和机器专属配置留在本地。
-   数据库、私人对话和个人记忆不默认进入 Git。
-   未来若迁移存储，需明确导出格式、版本和恢复流程；当前不提前建设。

------------------------------------------------------------------------

## 13. 安全

-   源码不含密钥、令牌和密码；`.env` 不提交。
-   模型拿不到 HA 地址和令牌，只能调用结构化工具。
-   高风险操作需要代码层权限检查与确认。
-   外部输入和模型生成的工具参数都需要校验。
-   不提交 `.env`、数据库、日志、缓存、Docker volume 和 `__pycache__`。
