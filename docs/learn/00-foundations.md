## 0. 先定个调：你只需要知道到什么程度

你现在会**读 Python**——这意味着你懂"变量、函数、if、循环、读文件"这种程序内部的逻辑。你不懂的是**程序怎么跑起来、怎么跟别的程序说话、怎么被打包**。

JARVIS 这个项目恰好就是由这几块"你不懂的部分"拼起来的。所以这份通识只补那几块：

每课都四段：**是什么 / 原理（用类比）/ 本项目里干什么 / 还能用在哪**。

## 第 1 课：Docker —— 把"运行环境"装进一个盒子

### 是什么
Docker 是一种**把软件连同它需要的整个运行环境一起打包、到处都能一模一样跑**的技术。

### 原理（类比）
你写过 Python 脚本吧：在你电脑能跑，发给同事却跑不起来——因为他没装那个库、或者库版本不同、或者他是 Mac 你是 Windows。

Docker 的解法：把"程序 + 它依赖的所有东西（库、配置、甚至一个迷你操作系统）"打包成一个**镜像（image）**，谁拿到这个镜像，运行起来就是一个**容器（container）**——一个隔离的小盒子，里面环境跟你开发时一模一样，跟宿主机的其他东西互不干扰。

几个关键名词：
- **镜像 image** = 盒子的"模板/快照"，只读。
- **容器 container** = 镜像跑起来的"一个活实例"。同一个镜像可以同时跑多个容器。
- **compose** = 一份 YAML，描述"要起哪几个容器、它们之间怎么连"，一条命令全起来（我们用 `docker-compose.yml`）。
- **端口映射** = 容器像住在盒里，外面默认访问不到。 `-p 8123:8123` 相当于在盒子上开个洞，让"本机的 8123"通往"盒子的 8123"。

### 在本项目里干什么
- Home Assistant 官方**只发布 Docker 镜像**，不发布 Windows 安装包。所以我们用 Docker 把这个"HA 盒子"跑起来。
- `docker-compose.yml` 描述：起一个名为 `jarvis-homeassistant` 的容器，把宿主机 `homeassistant/config/` 挂进盒子的 `/config`，并把盒子的 8123 开洞到本机 8123。
- 将来要跑 Ollama（本地大模型）时，也是加一个容器，compose 一起起。

### 还能用在哪
几乎所有"想到处都能跑、不想配环境"的服务：网站后端、数据库（MySQL/Postgres）、Redis、AI 模型服务、CI 流水线……你现在用的任何 SaaS 后台，大概率都跑在容器里。

## 第 2 课：HTTP 与 REST —— 两个程序之间怎么"寄信"

### 是什么
**HTTP** 是互联网上最通用的"程序之间说话"的规则。**REST** 是建立在 HTTP 之上、用一套约定去"操作资源"的风格。

### 原理（类比）
把一次 HTTP 通信想象成**寄一封信**：
- **信封地址（URL）**：比如 `http://localhost:8123/api/states/light.living_room`，告诉对方"我要找哪个资源"。
- **动作（方法）**：信上写"我要干嘛"——`GET`=查一下、`POST`=做一件事、`PUT/PATCH`=改一下、`DELETE`=删掉。
- **信的内容（body）**：要带的数据，通常是 JSON 格式（长得像 Python 字典）。
- **回信（响应）**：对方回一封，信封上盖个**状态码**——`200` 成功、`401` 你没权限、`404` 找不到、`500` 对方内部炸了；信里是返回的数据。

**REST** 就是约定：用 URL 表示"资源"、用方法表示"动作"。例如：
- `GET /api/states/light.living_room` → "查客厅灯现在状态"
- `POST /api/services/light/turn_on` + body `{entity_id: light.living_room}` → "开客厅灯"

### 在本项目里干什么
- **JARVIS 应用 → Home Assistant**：JARVIS 要开灯时，就发一个 HTTP POST 请求给 HA 的"开灯服务"。
- **健康检查**：JARVIS 周期性发 `GET /api/` 探 HA 在不在。
- **你将来用网页控制**：网页也通过 HTTP 把"打开客厅灯"这句话发给 JARVIS。

### 还能用在哪
你每天用的几乎所有网站和 App：打开抖音是 App 通过 HTTP 向服务器要数据；微信发消息也是 HTTP。只要"一个程序要找另一个程序要东西/做东西"，基本就是它。

## 第 3 课：API —— 程序的"对外窗口"

### 是什么
**API（Application Programming Interface）= 应用程序对外提供的"窗口/接口"**。你不用懂它内部怎么实现，只要按它规定的格式发请求，它就给你结果。

### 原理（类比）
就像 **ATM 机**：你插卡、按"取 500"，机器吐钱。你完全不需要懂里面怎么数钞、怎么跟银行通信——你只用了它暴露给你的"按钮"（接口）。这个"按钮的集合"就是 ATM 的 API。
对程序来说也一样：HA 暴露了"开灯""查温度"这些按钮（API 端点），JARVIS 只管按按钮，不用懂灯是怎么亮的。

### 在本项目里干什么
项目里有**两套 API**：
1. **HA 的 REST API**：JARVIS 通过它控制/查询虚拟设备（上一课的例子）。
2. **JARVIS 自己的 API**：我们自己用 FastAPI 写的，将来给网页/你调用（第一个端点就是 `/api/health`）。

### 还能用在哪
调用任何第三方能力都是调 API：微信登录、支付宝付款、高德地图、ChatGPT、天气查询……互联网就是一堆互相调 API 的程序。

## 第 4 课：FastAPI 与"JARVIS 应用" —— 一个一直监听的程序

### 是什么
**FastAPI** 是一个帮我们快速写出"能接收 HTTP 请求的程序"的 Python 框架。**JARVIS 应用**本身，本质就是一个"启动后一直运行、监听某个端口、等着别人发 HTTP 请求过来"的 Python 程序。

### 原理
- **端口监听**：程序说"我监听 8000 端口"，就像在 8000 号窗口后面坐了个柜员。别人朝 `localhost:8000` 发请求，就被这个柜员接到。
- **路由（route）**：柜员手里有张表——"URL 是 `/api/health` 的，交给 health 函数处理"。FastAPI 帮我们管理这张表和请求/响应的格式。
- 所以我们写的 `main.py` 就是：定义"收到 `/api/health` 时返回什么"，然后 `uvicorn` 把它跑起来监听 8000。

### 在本项目里干什么
- `main.py` + FastAPI 启动了 JARVIS 应用，监听 `127.0.0.1:8000`。
- `/api/health` 是我们暴露的**第一个窗口**：别人问"你活着吗、HA 连上了吗"，它回 JSON。
- 未来所有对话、控制，都通过在这个程序里加更多"路由（窗口）"来实现。

### 还能用在哪
任何"后端服务"：你公司内部的工具网站、数据接口、微信小程序后台……几乎都是某个框架（FastAPI / Flask / Django / Spring）启动一个监听程序。

## 第 5 课：YAML —— 给人读、给人改的配置

### 是什么
**YAML** 是一种写配置文件的格式，特点是"靠缩进表示层级，像大纲一样好读"。

### 原理
对比一下你就懂：JSON 写配置要一堆花括号和引号，YAML 靠缩进。本项目里你看到的：
```yaml
input_boolean:
  lr_light:
    name: "客厅灯"
    initial: off
```
`lr_light` 是 `input_boolean` 下面的一个配置项，它又有 `name`、`initial` 两个子项——缩进就表达了"谁属于谁"。

### 在本项目里干什么
两处核心配置都是 YAML：
- `docker-compose.yml`：描述起哪些容器。
- `homeassistant/config/packages/virtual_home.yaml`：描述"虚拟家庭有哪些设备"。
为什么用配置而不是写代码？因为"家里有哪些设备"是**给人类读、给人类改**的东西，不是程序运行时算出来的。改 YAML 比改代码安全、直观。

### 还能用在哪
现代基础设施几乎全是 YAML：Kubernetes、GitHub Actions（CI）、GitLab CI、Ansible……你以后只要看到 `.yml` 文件，就知道"这是配置"。

## 第 6 课：Home Assistant —— 智能家居的"翻译中枢"

### 是什么
**Home Assistant（HA）** 是一个开源的"智能家居中枢"软件。它统一管理家里所有设备（真的假的都行），对外提供统一的控制接口。

### 原理（为什么需要它）
你家的设备千奇百怪：灯用一种协议、空调用另一种、窗帘又一种。如果让 JARVIS 直接去控制每种设备，JARVIS 就得懂几百种"方言"。
HA 的价值就是**翻译层**：它自己懂各种设备的方言，然后对外只说一种"普通话"（它的 REST API）。于是 JARVIS 只要跟 HA 说"开灯"，HA 负责翻译成具体设备的语言。

**虚拟设备**：HA 还允许你"凭空造设备"——用 YAML 定义几个"状态底板"，再包装成真设备。我们没有真灯，就造了虚拟灯，但控制链路上和真灯一模一样。这就保证了：**将来把虚拟灯换成真灯，JARVIS 一行代码都不用改**（只改 HA 配置）。

### 在本项目里干什么
- HA 是整条链路里"最下游的执行者"：JARVIS 的指令最终都由 HA 落地到虚拟设备的状态上。
- 它跑在 Docker 盒子里（第 1 课），JARVIS 通过 HTTP（第 2 课）调它的 API（第 3 课）来指挥它。

### 还能用在哪
真实的智能家居：你买小米/涂鸦/Aqara 设备，接入 HA，就能用一个 App 统一控制、写自动化。很多人用 HA 管全屋。

## 第 7 课：LLM 与 tool calling —— 让大模型"真的会干活"

### 是什么
- **LLM（大语言模型）**：能读人话、写人话的 AI 模型（如 ChatGPT、通义、Qwen）。
- **tool calling（工具调用）**：让模型在听懂你意图后，输出"我要调用某个函数 + 参数"，而不是自己瞎编一句话。

### 原理（关键认知）
**LLM 本身不会"开灯"这个动作**——它只会生成文本。tool calling 的巧妙之处：我们提前告诉模型"你有三个工具可用：`turn_on_light(room)`、`set_ac(...)`、`get_temperature(...)`"。模型听懂"打开客厅灯"后，输出的是结构化指令：
```
调用 turn_on_light(room="living_room")
```
然后**由我们的代码去真正执行这个调用**（发 HTTP 给 HA 开灯）。模型只负责"决策调哪个工具、填什么参数"，**动作永远由代码做**。

- **Stub（替身模型）**：一个"假的"模型，行为写死（比如永远返回"调 turn_on_light"）。我们用它在没有真模型时，把整条链路测通、验证逻辑对不对。等真模型（Ollama）接上，直接替换，上层不用动。

### 在本项目里干什么
- `llm/stub_provider.py` 就是那个替身，Phase 1 就位，让后面 7 个阶段不用等真模型也能开发测试。
- 将来 `ollama_provider.py` 接真实模型，做真正的"听懂人话"。

### 还能用在哪
所有 AI Agent、智能助手、自动化流程：客服机器人、代码助手、数据分析 Agent……核心套路都是"LLM 决策 + 代码执行工具"。

## 第 8 课：WebSocket —— 打通的电话（对比 HTTP）

### 是什么
**WebSocket** 是一种"建立一次连接后持续双向通信"的协议，与 HTTP 的"问一句答一句就挂断"相对。

### 原理（类比）
- **HTTP** = 寄信：你写一封问、对方回一封、结束。
- **WebSocket** = 打电话：拨通后双方一直在线，随时互说。
适合"需要持续交互或服务器主动推消息"的场景。

### 在本项目里干什么
HA 取**长期访问令牌（LLAT）**的那一步，用的是 WebSocket 命令（`auth/long_lived_access_token`），不是普通 HTTP 请求。这是 HA 2026.9 的认证机制决定的。

### 还能用在哪
聊天室、股票实时行情推送、在线协作编辑（如飞书文档）、游戏同步——任何"数据要实时双向流动"的地方。

## 第 9 课：环境变量与 .env —— 不写死在代码里的配置

### 是什么
**环境变量**是"程序运行时才能确定的值"，从外部注入，不写进代码。**`.env`** 是存这些值的本地文件。

### 原理
代码里写 `ha_token = os.getenv("JARVIS_HA_TOKEN")`（读环境变量），而**具体的值**放在 `.env`：
```
JARVIS_HA_TOKEN=eyJxxx...长串令牌
```
为什么这么绕？两个原因：
1. **密钥不能进代码、不能进 Git**（会泄露）。`.env` 被 `.gitignore` 排除，永不提交。
2. **换机器只改 `.env`，不碰代码**。你单位机器和家里机器，HA 地址/令牌不同，但代码完全一样。

本项目所有机器相关配置（`JARVIS_HA_URL`、`JARVIS_HA_TOKEN`、`JARVIS_LLM_PROVIDER`…）都走这个机制，`config.py` 负责读取。

### 还能用在哪
任何项目都该这么干：数据库密码、API key、环境切换（dev/prod）……这是工程基本功。

## 第 9.5 课：鉴权与令牌（token）—— 程序怎么"证明自己是谁"

> 这一课紧接第 9 课。第 9 课讲了"密钥放在哪"，这一课讲"密钥到底是什么、为什么需要它、怎么用"。它是理解 `JARVIS_HA_TOKEN` 的关键。

### 是什么
**鉴权（authentication）** = "证明你是你"；**令牌（token）** = 证明通过后，对方发给你的一张"临时/长期通行证"。

前面第 2、3 课说过：JARVIS 每次要给 HA 发 HTTP 请求调设备。但 HA 不能谁都能调（否则别人也能开你家的灯）。所以 HA 要求：**每个请求都必须带着一张"我有权限"的通行证**。`JARVIS_HA_TOKEN` 就是这张通行证，正式名叫 **long-lived access token（长期访问令牌，LLAT）**。

### 原理（类比）
把 HA 想成带门禁的小区：
- **账号密码** = 你在物业登记时用的身份（只在"办证"那一步用一次）。
- **令牌 token** = 物业给你的一张门禁卡。"谁拿着这张卡，谁就能进门"——所以它是个秘密，不能公开。
- **Bearer Token（持票人令牌）** = 一种特殊的卡：规则是"**见卡即放行**，不查持卡人是不是本人"。简单高效，但代价是卡一旦丢失，捡到的人也能进。所以 token 必须保管好（放 `.env`，不进 Git）。

HA 的令牌分两种，我们正好都用过：
- **短令牌（access token）**：办证流程中临时领的，约 30 分钟过期。只用来"开门取长期卡"，用完即弃。
- **长令牌 LLAT（`JARVIS_HA_TOKEN`）**：一旦办下**永不过期**，存起来反复用。这就是写进 `.env` 的那张"长期门禁卡"。

### 在本项目里具体干什么（我查了真实代码）
- **从哪来** —— `src/jarvis/config.py`：
  ```python
  ha_token: str = ""   # 配合文件顶部的 env_prefix="JARVIS_"
  ```
  因为设了 `env_prefix="JARVIS_"`，代码里的 `ha_token` 实际从**环境变量 `JARVIS_HA_TOKEN`** 读取，值写在项目根目录的 `.env` 里。
- **怎么用** —— `src/jarvis/ha/client.py` 第 59 行：
  ```python
  return {"Authorization": f"Bearer {self._token}"} if self._token else {}
  ```
  JARVIS 每发一个 HTTP 请求给 HA，都会在请求头里带 `Authorization: Bearer <那串令牌>`。HA 见到就放行。
- **没它会怎样**（同一文件）：
  - 第 84 行：没配置 → 健康检查报 `"未配置 JARVIS_HA_TOKEN"`
  - 第 99 行：令牌错/没权限 → `"令牌无效或权限不足（检查 JARVIS_HA_TOKEN）"`

它在链路里的位置：
```
你说"开灯" → JARVIS(:8000) --HTTP 带 Bearer 令牌--> HA(:8123) 验令牌 → 开灯
                                      ↑ 这把钥匙就是 JARVIS_HA_TOKEN
```
**为什么不能直接用 HA 账号密码？** 因为 HA 的 API 不认"账号+密码"进请求，它只认 token。账号密码只在"办证生成 LLAT"那一步用一次，之后 JARVIS 只靠令牌干活。

**它是怎么"办"出来的（HA 2026.9 的机制）**：
1. 先走一次 onboarding 登录，拿到**短令牌**（约 30 分钟有效）。
2. 用短令牌通过 **WebSocket**（第 8 课）发一条命令 `auth/long_lived_access_token`，HA 才发给你那张**长期卡 LLAT**。
3. 把 LLAT 存进 `.env` 的 `JARVIS_HA_TOKEN`，以后 JARVIS 永久用它。

### 还能用在哪
`JARVIS_HA_TOKEN` 背后的模式叫 **API Key / Bearer Token 鉴权**，是互联网最通用的"程序对程序"开门方式：
- 调 GitHub API、OpenAI API、Stripe、Google 地图、AWS……全都是"在请求头里带 `Authorization: Bearer xxx`"。
- 你以后写任何"我的程序要调某个外部服务"的东西，都会遇到一模一样的 token。
- "把密钥放进 `.env`、绝不写进代码、绝不提交 Git"这个习惯，是所有涉及密码/令牌场景的**铁律**——和我们这个 token 的处理方式完全一样。
- 安全提醒：它是秘密，只在本地 `.env`；本项目是**虚拟家庭**，别人拿到也只能开虚拟灯，风险低，但习惯要养好；要作废就去 HA 界面"长期访问令牌"里删掉重新生成。

## 第 10 课：串讲 —— 你说"打开客厅灯"，到底发生了什么

把上面所有技术串成一次完整旅程。**注意每一跳是哪个技术在干活**：

1. **你**说："打开客厅灯"
2. （将来）**网页**通过 **HTTP** 把这话发给 **JARVIS 应用**（监听在 `localhost:8000` 的 FastAPI 程序）
3. **JARVIS 的 Agent**：用 **LLM**（或规则）听懂意图 → 决定调用工具 `turn_on_light(room="living_room")`
4. **Tool 层**：把"客厅灯"翻译成设备 ID `light.living_room`，交给 `HomeAssistantClient`
5. **HomeAssistantClient**：发一个 **HTTP POST** 请求，通过 **HA 的 REST API**，调用"开灯"服务
6. **Home Assistant**（跑在 **Docker** 盒子里）：收到请求，去翻转虚拟设备 `light.living_room` 的底层状态（那个 `input_boolean` 底板）
7. **HA** 回 **HTTP 200** 成功
8. **JARVIS** 把结果组织成"已打开客厅灯"，沿原路返回给你

> 这一趟里：Docker（承载 HA）、HTTP/REST（通信规则）、API（HA 的窗口）、FastAPI（JARVIS 的监听程序）、YAML（定义虚拟设备）、LLM/tool calling（理解意图并决策）、.env（提供令牌让请求有资格）——全部各司其职。**你现在已经知道每一块是干什么的了。**
