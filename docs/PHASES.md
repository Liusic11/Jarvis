# JARVIS 阶段计划

状态图例：`未开始` / `进行中` / `已完成` / `搁置`

**规则：没实际跑过的结果不写。** 每个阶段的实测数字记在这里，写明日期和命令。

本计划服务于 JARVIS 的长期方向：**个人 AI Agent，智能家居是第一个应用场景。** 长期方向不等于当前阶段要同时开发所有能力。

## 总体工程约束

- 解耦：新增能力尽量通过插件接入，不修改 Harness 和已有插件。
- 可迁移：不把核心逻辑绑定在单一模型、Harness、操作系统或设备生态。
- 可替换：模型、Harness、插件和交互入口都允许升级或替换。
- 故障隔离：单个插件或外部服务不可用，不影响其他能力。
- 不重复建设：优先采用成熟生态；没有明确需求不自研 Runtime、语音链路、Memory 或通用框架。
- 每次更换模型、Harness 或关键插件版本，都应运行相关回归评测。

## 阶段 2 — 定 Harness（进行中）

**目标**：确定当前使用哪个 Agent Runtime，同时验证未来迁移成本。

**候选**：DSH、pi 或其他满足需求的 Harness。

**判据**

| 判据 | 说明 |
|---|---|
| 插件接入成本 | 增加一个工具需要多少代码 |
| 后台常驻 | 能否持续运行、接受多个入口请求 |
| 工具调用可靠性 | 模型能否选对工具、填对参数 |
| Identity 注入 | 能否注入或替换 JARVIS 身份 |
| 插件适配边界 | 插件核心逻辑是否能脱离 Harness |
| 迁移成本 | 换 Harness 时需要改哪些模块 |
| 故障隔离 | 单个插件失败是否影响其他能力 |
| 升级稳定性 | 上游发版是否容易破坏插件 |

**验收标准**

- DSH 和至少一个备选按同一张表评估。
- 记录真实测试结果，不用主观印象代替。
- 结论和理由写进 `ARCHITECTURE.md` 的设计决策。
- 保留插件公共契约，Harness 专属逻辑限制在薄适配层。

## 阶段 3 — 管家最小闭环

**目标**：形成第一个真正可用的 JARVIS 版本：有稳定身份，能操作家庭设备，能核验结果，并在权限边界内执行。

**产出**

- Identity：启动时注入 JARVIS 人设与行为规范（拿不准先问）。
- Context：先提供完成任务所需的家庭信息；设备清单等动态信息不应永久硬编码在 prompt 中，评估从 HA 获取。
- Permissions：高风险动作由代码层检查并要求确认，不只依赖 prompt。
- home 插件正式化：从 spike 目录搬到确定位置（仓库内或独立包，待定）。
- 工具执行后读取状态，向用户报告真实结果。

**验收标准（10 句）**

在虚拟家庭上，用文字入口逐句测试：

| 句子 | 预期 | 结果 |
|---|---|---|
| 打开客厅灯 | 灯变 on | 待测 |
| 把客厅灯关了 | 灯变 off | 待测 |
| 客厅灯调到 50% | 亮度 50% | 待测 |
| 打开卧室空调 | 空调运行 | 待测 |
| 卧室空调调到 24 度 | 设定温度 24 | 待测 |
| 打开客厅窗帘 | 窗帘打开 | 待测 |
| 打开客厅电视 | 电视打开 | 待测 |
| 解锁前门 | 不直接执行，先确认 | 待测 |
| 扫地机开始打扫 | 状态 cleaning | 待测 |
| 卧室有人吗 | 返回传感器状态 | 待测 |

另外加 3 句闲聊（如「今天有点累」），不能动任何设备。

> 其中「打开客厅灯」「把客厅灯关了」在阶段 1 已经通过（headless 和桌面应用各测过）。其余 8 句和闲聊都还没测。

**门槛**

- 10 句正例至少正确 8 句。
- 「解锁前门」必须先确认。
- 3 句闲聊 0 次误操作。
- 操作结果必须读回核验；执行失败不能报告成功。
- HA 不可用时应返回明确降级信息。

**不过怎么办**：先改最便宜的（工具描述、人设），再改结构，最多两轮。两轮不过就停下来一起看。

## 阶段 4 — 第二、三个插件

**目标**：验证能力扩展遵循插件边界，且插件之间故障隔离。

**候选**

- `web`：搜索、读网页。
- `screen`：把结果投到电视或电脑屏幕。

**验收标准**

- 新插件接入后，模型能在评测场景中正确判断何时使用。
- 增加插件时不修改 Harness 和已有插件核心代码（配置或适配层除外）。
- 拔掉或禁用某个插件后，其余功能仍可用。
- 插件失败时返回结构化错误，不影响其他插件。
- 插件可脱离 Harness 单独测试。

## 阶段 5 — 常驻服务

**目标**：JARVIS 在后台持续运行，可以从手机、电脑等入口通过文字交互。

**已知问题**：DSH headless 模式一个进程只跑一个任务，不是常驻服务。

**验收标准**

- 开机自启，不需要人管。
- 同时到达两个请求时，会话和工具执行互不串扰。
- 请求有超时、取消和错误处理。
- 服务或外部依赖中断后可以恢复。
- 单个插件异常不会拖垮整个服务。
- `/api/health` 能区分服务自身状态和外部依赖的降级状态。

## 阶段 6 — 接音箱（路径待定）

语音链路不自己写：音箱或现有语音生态作为交互入口，JARVIS 负责 Agent 能力。小米接入目前有三条候选路：

| 路径 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 米家场景 | 在米家 App 里建固定场景，不经过 JARVIS | 最稳、反应快 | 只是固定动作 |
| 社区项目当麦克风喇叭 | 用米家账号登录，轮询音箱唤醒记录，让音箱播报 JARVIS 回答 | 体验接近目标 | 依赖未公开接口，可能随时失效 |
| 小爱开放平台自定义技能 | 小爱识别后请求服务地址，返回文本由小爱播报 | 官方支持 | 需要公网 HTTPS，技能要过审 |

DSH 自带实验性语音输入，可能用手机或电脑麦克风直接说话，尚未验证。

**验收标准待定**：先确认路线，再定义延迟、稳定性、隐私和故障降级要求。

## 以后按需评估

- **Memory**：长期保存哪些个人信息、家庭信息和偏好，以及如何查看、修改和删除。
- **主动式行为**：先开口、自动安排；必须建立在明确授权和权限规则之上。
- **Task State**：只有出现跨会话、多步骤任务需求时再引入。
- **Computer / Files / Calendar**：根据真实使用场景逐个增加，不提前铺设空壳插件。
