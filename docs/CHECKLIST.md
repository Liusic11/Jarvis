# JARVIS 执行清单

这份清单按顺序走，每一步写明你要做什么、我做什么、怎么算完成。

**怎么用**：做完一项把 `[ ]` 改成 `[x]`。到「你回来告诉我」那一步就停下找我，后面的交给我。

**卡住的规则**：门槛不过时先改最便宜的（工具描述、人设），再改结构，最多两轮。两轮不过就停下来一起看。

相关文档：[阶段计划](PHASES.md)、[架构](ARCHITECTURE.md)、[硬件成本](research/2026-11-26-local-llm-hardware-cost.md)、[智能家居](research/2026-11-26-smart-home.md)。

## 第 0 步：路线（已定）

- [x] JARVIS 是长期演进的个人 AI Agent，智能家居是第一个应用场景，不是项目边界。当前只做任务型闭环：给一个任务，它完成并回复。
- [x] 四条架构原则：解耦、可迁移、可替换、故障隔离与优雅降级。核心原则是「JARVIS 应该拥有体验，而不是拥有基础设施」。
- [x] 语音不自己写，音箱当「嘴和耳朵」。
- [x] harness 可替换，不绑死某一个；DSH 先试。
- [x] 场景以插件形式存在，管家的手脚约等于插件。
- [x] 身份与能力分离：当前用 system prompt 在启动时注入，以后可以换成动态的上下文来源。
- [x] 高风险动作必须由代码层控制并要求确认，不能只靠 prompt。**还没实现**，排在第 3 步。
- [ ] 音箱走哪条路：**待确认**，三条候选见 `PHASES.md` 阶段 6。

## 第 1 步：Harness spike（已完成，2026-11-27）

- [x] 给 DSH 写了 home 插件（约 190 行），在仓库外：`D:\dsh-plugins\dsh-plugin-home`。
- [x] 无界面模式跑通：开灯、关灯。

## 第 3 步：身份、上下文和权限

**我做什么**：

- 身份：写 system prompt，分三块：人设、这个家、你的习惯。其中写明「拿不准先问」「做完读回状态」。
- 上下文：先弄清哪些家庭信息放 prompt、哪些该从 Home Assistant 现取。
- 权限：在 home 插件里加检查，让「解锁前门」这类动作必须先确认。现在的插件什么服务都放行。

**你做什么**：

- [ ] 告诉我你希望管家是什么性格、怎么称呼你、说话什么风格。
- [ ] 看几段对话示例，满意为止。
- [ ] 决定哪些动作算高风险（至少是门锁）。

**完成标志**：同一个任务，换掉身份后管家的表现明显不同；说「解锁前门」时它不会直接动手。

## 第 6 步：修虚拟灯的问题

- [ ] 客厅灯关着的时候，带亮度说「客厅灯调到 50%」，灯不会亮，只会改亮度。

这是 Home Assistant 模板灯的行为，和插件无关。验收之前修掉，免得「客厅灯调到 50%」这句误判。
